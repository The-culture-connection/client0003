# Release builds — Expansion mobile app

How to produce a signed Android App Bundle pointed at a specific Firebase
project. Internal beta (Weeks 1–2) runs on `mortar-stage`; see
[BETA_TESTING_PLAN.md](BETA_TESTING_PLAN.md) §4.

## The one rule

**An environment is two files, and they must agree.**

| Layer  | File | Reaches |
| ------ | ---- | ------- |
| Native | `android/app/google-services.json` | FCM push, Crashlytics |
| Dart   | `lib/firebase_options.dart` (`DefaultFirebaseOptions`) | Auth, Firestore, Storage, Functions |

`main.dart` calls `Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)`
with explicit options, so the Dart layer does **not** read `google-services.json`.
Change only one of the two and the app splits its traffic: push tokens register
against one project while Firestore reads another. Nothing errors — it just
silently sends beta users' data to the wrong place.

`tool/build_stage_aab.ps1` changes both together and restores afterwards. Use it
rather than editing either file by hand.

## Building

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tool\build_stage_aab.ps1
```

Defaults to `mortar-stage`; pass `-FirebaseEnv dev` for a dev-pointed bundle.
Output: `build/app/outputs/bundle/release/app-release.aab`.

The script preflights before spending build time: the config exists, its
`project_id` matches, a Firebase app is registered for the `applicationId`
(`com.expansionnetwork.expansion_network`), and `android/key.properties` is
present. It swaps `google-services.json` in, builds with
`--dart-define=FIREBASE_ENV=stage`, and restores the dev config in a `finally`
block — so a failed or interrupted build never leaves the checkout pointed at
stage. Pass `-KeepConfig` to skip the restore when iterating.

`FIREBASE_ENV` defaults to `dev`, so a plain `flutter run` is unaffected. An
unrecognised value throws at startup instead of falling back to dev.

## Adding an environment

1. Register the Android app under `com.expansionnetwork.expansion_network` in
   the target Firebase project.
2. `firebase apps:sdkconfig ANDROID <appId> --project <projectId> --out android/config/google-services.<projectId>.json`
3. Add matching `_androidX` / `_iosX` blocks and a `switch` arm in
   `lib/firebase_options.dart`.
4. Add the name to the `ValidateSet` on `-FirebaseEnv`.

## Signing

`android/key.properties` supplies the upload key; the keystore lives at
`infra/Credentials/android-play-release/upload-keystore.jks`. `storeFile` is a
path **relative to `android/`** — keep it relative, since an absolute path
breaks whenever the checkout moves. `android/app/build.gradle.kts` fails
`bundleRelease` outright if signing properties are missing, rather than quietly
falling back to the debug key (which Play rejects).

## Before each Play upload

Bump `version:` in `pubspec.yaml` — Play rejects a bundle whose `versionCode`
(the number after `+`) is not higher than every previous upload on the track.

## Known gaps

- **iOS on stage has no OAuth client**, so Google Sign-In is unavailable in a
  stage iOS build until one is added in the Firebase console. Android is
  unaffected.
- `firebase_options.dart` carries a "generated by FlutterFire CLI" header.
  Re-running `flutterfire configure` overwrites the environment switch — re-apply
  it if you do.
